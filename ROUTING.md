# Selection routing and typed helpers

The generated catalog covers 208 selections across nine resources. The facade exposes 210 typed methods: 205 JSON selection helpers, three CSV helpers, and the `CompanyDetailed` and `TornStock` aliases. There are 224 raw JSON convenience methods: 205 for capabilities, including both generic-only and direct-only spellings, and 19 for v1-only selections without a published schema. Method counts describe API inventory, not statement or branch coverage.

```go
pair, err := torn.FetchPair(ctx, client,
    torn.UserSelections.Profile,
    torn.UserSelections.Job,
    map[string]any{"id": int64(123)},
    torn.RequestOptions{},
)
if err != nil { return err }
profile := pair.First // models.UserProfileResponse
job := pair.Second   // models.UserJobResponse
_ = profile
_ = job
```

This performs one request to `/v2/user?selections=job,profile&id=123`. Results retain the concrete response envelopes, and `pair.Report.Calls` identifies the successful contributing request. Tokens carry an unexported resource identity: mixing `UserSelections.Profile` with a faction token fails Go type inference. A dynamically chosen string list guarantees validated routing and merged raw JSON; it cannot establish a compile-time response type. Use `DecodeSelections[T]` for an explicit custom decoder, or `RawSelections` for the merged raw response. Independent helper calls each execute independently.

`PlanSelections` trims, lowercases, deduplicates, and sorts selections. Compatible v2 selections form one generic call. Standalone selections (`user/log`, search endpoints) remain separate; direct-only paths consume their documented path parameters. Documented v1-only compatibility selections share one v1 call, except names that the v2 selection enum lists as served by Torn's own v1 fallback (user `bazaar`, `criminalrecord`, `display`; torn `competition`, `organisedcrimes`), which join the v2 generic call and are re-planned on v1 if Torn answers code 22. Selection names the SDK does not know are sent as v2 generic selections (P1.5). CSV snapshots are rejected by JSON batching and are exposed by `UserSnapshot`, `FactionSnapshot`, and `CompanySnapshot` as text.

Each batch shares one target and filter map. Different categories, date ranges, or IDs require separate batches. Documented query parameters are restricted to the generic or exact endpoint's allowlist; parameters that no endpoint of the resource documents (new upstream filters) are forwarded verbatim to every call of the plan. The planner maps a supplied `id` to a required exact-path identifier when needed; explicit aliases such as `crimeId`, `tradeId`, `typeId`, and `propertyTypeId` are supported. Generic-only ID domains map those aliases back to `id`. `user/trade` and `user/crimes` cannot share a batch with profile/job because their identifier denotes a trade or crime rather than a user. They can share a request with neutral `timestamp` or `lookup` selections. Missing required identifiers fail before sending.

API v2 generic membership requires an official enum entry and an associated documented generic response branch. The current spec spells the generic faction selection `dirtbombs`, with a different direct-only `/faction/dirtybombs` path; both are retained. It similarly distinguishes generic `user/itemmod` from direct `user/itemmods`. `user/factionbalance` is generic-only. Company `companies` is in the generic enum, but the generic response contract omits its response schema; it uses `/company/{typeId}/companies` conservatively. All remaining company generic response associations can batch normally.

`spec/routing-overrides.json` records these associations, compatibility bundle types, and documented legacy selections. `spec/routing-manifest.json` maps each capability to its exact operation IDs, paths, query allowlists, required path parameters, and response schema. Run `go run ./cmd/generate-routing` offline after editing the pinned specification or metadata. Both artifacts are generated by Go.

Legacy payloads without an authoritative full v1 contract use named compatibility bundles. Their dynamic/exact JSON fields remain explicitly identified in the compatibility report; naming a bundle does not imply a verified historical wire schema. Current typed helpers use current `models` envelopes wherever one documented concrete envelope exists. Mixed-shape operations use compatibility bundles with their documented custom decoding behavior. CSV snapshots and legacy aliases retain their distinct channel/shape semantics.

The executor splits a combined request rejected with code 4 or 22 (or HTTP 400/404/501) into single-selection requests. Code 22 on a single selection re-plans it once on v1, and code 23 on a v1 call re-plans it once on v2 (P4.3). Recovery after code 4 or HTTP 400/404/501 on v1 additionally requires `RequestOptions{AllowLegacyFallback:true}` and a planned fallback route. Message text is never used for classification. Reports contain successful calls, omitting failed attempts. An explicit plan remains available through `Client.Execute` for callers that need precise control.

The independent v1 compatibility catalog contains 184 selection/resource pairs: user 66, faction 53, Torn 50, market 9, property 3, and company 3. `V1Catalog()`, `LegacySelections()`, and `SupportsV1Selection(resource, selection)` expose independent copies and membership checks. `PlanV1Selections` (also named `PlanLegacySelections`) deliberately requests these v1 routes. `PlanSelections` also recognizes catalog-only legacy names outside the 208 current capabilities, including faction `armorynews` and Torn `chainreport`. Only explicit catalog members receive an automatic fallback route; forum, racing, and key selections never do. Property v1 support is maintained explicitly even though its v2 generic endpoint has no `legacy` parameter.

`spec/v1-catalog.json` is the maintained compatibility contract and includes the exact v1 filter allowlist. Current official schema descriptions corroborate legacy-only names and named fallback selections; migrated entries preserve existing SDK routing support. The lack of a complete authenticated historical v1 specification remains an evidence limitation. Catalog membership establishes intended routing compatibility, not independently verified payload typing or permanent endpoint availability. Callers can inspect plans before execution and must opt into runtime v1 recovery.

Planner verification includes both pinned specification inventories, more than 2,000 compatible-pair checks at the actual HTTP transport, full compatible groups, explicit generic/direct/standalone/legacy bucket lower bounds, identifier-domain rejections, all 224 raw helpers, and all 210 typed helpers including CSV. Response fixtures for documented models come from independent official contract sampling; compatibility fixtures use explicit envelopes. The frozen specification provenance limitations are documented separately and are not waived by routing tests.
