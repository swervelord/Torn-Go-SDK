# Selection routing and typed helpers

The generated catalog covers 207 selections across nine resources. The facade exposes 209 typed methods: 204 JSON selection helpers, three CSV helpers, and the `CompanyDetailed` and `TornStock` aliases. There are 204 raw JSON convenience methods, including both generic-only and direct-only spellings. Method counts describe API inventory, not statement or branch coverage.

```go
pair, err := torn.FetchPair(ctx, client,
    torn.UserSelections.Profile,
    torn.UserSelections.Job,
    map[string]any{"id": int64(123)},
    torn.RequestOptions{},
)
if err != nil { return err }
profile := pair.First // models.UserProfileResponse
job := pair.Second   // models.UserJobResponse
_ = profile
_ = job
```

This performs one request to `/v2/user?selections=job,profile&id=123`. Results retain the concrete response envelopes, and `pair.Report.Calls` identifies the successful contributing request. Tokens carry an unexported resource identity: mixing `UserSelections.Profile` with a faction token fails Go type inference. A dynamically chosen string list guarantees validated routing and merged raw JSON; it cannot establish a compile-time response type. Use `DecodeSelections[T]` for an explicit custom decoder, or `RawSelections` for the merged raw response. Independent helper calls each execute independently.

`PlanSelections` trims, lowercases, deduplicates, and sorts selections. Compatible v2 selections form one generic call. Standalone selections (`user/log`, search endpoints) remain separate; direct-only paths consume their documented path parameters. Documented v1-only compatibility selections share one v1 call. CSV snapshots are rejected by JSON batching and are exposed by `UserSnapshot`, `FactionSnapshot`, and `CompanySnapshot` as text.

Each batch shares one target and filter map. Different categories, date ranges, or IDs require separate batches. Query parameters are restricted to the generic or exact endpoint's allowlist. The planner maps a supplied `id` to a required exact-path identifier when needed; explicit aliases such as `crimeId`, `tradeId`, `typeId`, and `propertyTypeId` are supported. Generic-only ID domains map those aliases back to `id`. `user/trade` and `user/crimes` cannot share a batch with profile/job because their identifier denotes a trade or crime rather than a user. They can share a request with neutral `timestamp` or `lookup` selections. Missing required identifiers fail before sending.

API v2 generic membership requires an official enum entry and an associated documented generic response branch. The current spec spells the generic faction selection `dirtbombs`, with a different direct-only `/faction/dirtybombs` path; both are retained. It similarly distinguishes generic `user/itemmod` from direct `user/itemmods`. `user/factionbalance` is generic-only. Company `companies` is in the generic enum, but the generic response contract omits its response schema; it uses `/company/{typeId}/companies` conservatively. All remaining company generic response associations can batch normally.

`spec/routing-overrides.json` records these associations, compatibility bundle types, and documented legacy selections. `spec/routing-manifest.json` maps each capability to its exact operation IDs, paths, query allowlists, required path parameters, and response schema. Run `go run ./cmd/generate-routing` offline after editing the pinned specification or metadata. Both artifacts are generated by Go.

Legacy payloads without an authoritative full v1 contract use named compatibility bundles. Their dynamic/exact JSON fields remain explicitly identified in the compatibility report; naming a bundle does not imply a verified historical wire schema. Current typed helpers use current `models` envelopes wherever one documented concrete envelope exists. Mixed-shape operations use compatibility bundles with their documented custom decoding behavior. CSV snapshots and legacy aliases retain their distinct channel/shape semantics.

The executor can split a rejected combined request into single-selection requests. Runtime v2-to-v1 recovery requires `RequestOptions{AllowLegacyFallback:true}` and a planned fallback route; it is disabled by default. Reports contain successful calls, omitting failed attempts. An explicit plan remains available through `Client.Execute` for callers that need precise control.

The independent v1 compatibility catalog contains 184 selection/resource pairs: user 66, faction 53, Torn 50, market 9, property 3, and company 3. `V1Catalog()`, `LegacySelections()`, and `SupportsV1Selection(resource, selection)` expose independent copies and membership checks. `PlanV1Selections` (also named `PlanLegacySelections`) deliberately requests these v1 routes. `PlanSelections` also recognizes catalog-only legacy names outside the 207 current capabilities, including faction `armorynews` and Torn `chainreport`. Only explicit catalog members receive an automatic fallback route; forum, racing, and key selections never do. Property v1 support is maintained explicitly even though its v2 generic endpoint has no `legacy` parameter.

`spec/v1-catalog.json` is the maintained compatibility contract and includes the exact v1 filter allowlist. Current official schema descriptions corroborate legacy-only names and named fallback selections; migrated entries preserve existing SDK routing support. The lack of a complete authenticated historical v1 specification remains an evidence limitation. Catalog membership establishes intended routing compatibility, not independently verified payload typing or permanent endpoint availability. Callers can inspect plans before execution and must opt into runtime v1 recovery.

Planner verification includes both pinned specification inventories, more than 2,000 compatible-pair checks at the actual HTTP transport, full compatible groups, explicit generic/direct/standalone/legacy bucket lower bounds, identifier-domain rejections, all 204 raw helpers, and all 209 typed helpers including CSV.
